# 技术选型与问题解答

更新日期：2026-08-09。

本文回答 StoryWeaver 为什么采用当前技术、这些技术解决了什么问题、实现中遇到了哪些故障，以及什么情况下应该更换方案。它面向答辩、交接、代码评审和后续维护，不代替 API 或运维手册。

## 一、核心技术选型总表

| 领域 | 选择 | 为什么选择 | 主要代价 |
| --- | --- | --- | --- |
| 前端框架 | Vue 3 + TypeScript | 组合式 API 适合复杂表单与工作台；类型可约束前后端 DTO | 大型页面仍需主动拆分，类型来自手工契约维护 |
| 构建工具 | Vite | 冷启动快、Vue 集成成熟、生产构建简单 | 大模块仍需代码分割和体积预算 |
| 服务端状态 | TanStack Vue Query | 查询缓存、失效、重试和 loading/error 状态统一 | 不能替代本地 UI 状态管理 |
| 客户端状态 | Pinia | 适合主题、工作区、流状态等跨页面状态 | 不应用来复制后端数据缓存 |
| 富文本编辑 | TipTap | 基于 ProseMirror，扩展性和结构化文档能力强 | 包体较大，长文本与扩展需性能测试 |
| UI 基础 | Element Plus + 自建语义样式 | 快速获得可靠 Dialog/Form 等组件，同时保持产品视觉 | 需要主题变量映射和可访问性复验 |
| 后端 | Java 21 + Spring Boot 4 | 事务、安全、JPA、可观测和生态完整，适合复杂业务规则 | 启动和构建比轻量框架重 |
| 架构 | 模块化单体 | 保留清晰领域边界，同时避免早期微服务的分布式事务 | 必须用包边界和 ArchUnit 防止模块腐化 |
| 主数据库 | PostgreSQL 18 | 强事务、约束、JSONB、数组、窗口查询和 pgvector 可共存 | 水平扩展和运维需要专业能力 |
| 向量检索 | pgvector + 本地 ONNX | 向量与业务所有权在同一事务域；可离线运行 | 当前精确检索不适合无限规模 |
| 缓存/协调 | Redis 8 | 适合短期协调、缓存和未来限流，不承担正式正典 | 增加一个运行依赖，不能当记录源 |
| 数据迁移 | Flyway | SQL 可审计、顺序明确、空库和存量库行为一致 | 已应用迁移不能随意修改 |
| 鉴权 | Spring Security + HS256 JWT | 无状态、部署简单，适合当前单体与同源前端 | 没有刷新/吊销；生产需更完善会话策略 |
| AI 供应商 | DeepSeek Adapter | 中文长文本与成本适配，封装后可替换 | 外部可用性、价格和模型行为会变化 |
| 实时进度 | 持久化事件 + SSE | 服务端单向推送适合生成进度，协议比 WebSocket 简单 | Bearer Token 下不能直接使用原生 EventSource |
| 测试 | JUnit、Testcontainers、Vitest、Playwright、axe | 覆盖领域、真实数据库、浏览器流程和可访问性 | 全量验证依赖 Docker，耗时高于纯 Mock |
| 部署 | Docker Compose | 一条命令还原数据库、缓存、应用和监控 | 适合本地/演示，不等于生产编排 |
| 可观测性 | Actuator、Prometheus、Grafana、Tempo | 指标、日志和 Trace 形成最小闭环 | 需要端口、数据保留和访问控制配置 |

## 二、架构类问题

### 为什么使用模块化单体，而不是微服务？

小说工作流审批会同时写入章节版本、候选事实、人物状态、物品归属、知识边界和工作流状态。这些数据需要一次事务完成。模块化单体可以直接使用 PostgreSQL 事务保证原子性，又能按 `auth/project/chapter/workflow/skill` 等包维持业务边界。

如果现在拆成微服务，就会引入分布式事务、消息最终一致性、重复消费、链路部署和跨服务调试，复杂度远大于收益。只有当团队、部署频率、容量或故障隔离需求明确超过单体边界时，才应按已有模块边界拆分。

### 为什么数据库是正典记录源，Redis 不是？

正典内容需要可追溯、可事务提交和可恢复。PostgreSQL 提供外键、唯一约束、乐观锁和事务；Redis 更适合短期协调。即使 Redis 数据丢失，已审批章节和正典也必须完整存在，因此 Redis 不保存唯一正式事实。

### 为什么 AI 输出不能直接写入正典？

模型可能产生幻觉、越过人物知识边界、改变物品归属或破坏时间线。StoryWeaver 把模型输出分为草稿、候选事实和审核意见，停在 `WAITING_APPROVAL`。只有用户审批后，系统才在单一事务中写入正式版本。

这不是额外流程装饰，而是长篇连续性系统的核心安全边界。

### 为什么章节版本采用追加而不是覆盖？

覆盖会丢失历史，也难以解释“某个事实从哪一版正文产生”。不可变版本允许对比、恢复、审计和回滚。恢复旧版本时创建新的当前状态，而不是修改历史行。

## 三、前端技术问题

### 为什么 Vue Query 和 Pinia 同时使用？

Vue Query 管理来自服务器的数据，例如项目、章节和工作流详情；Pinia 管理客户端状态，例如主题、侧栏、工作区和事件流连接状态。把服务器数据复制进 Pinia 会造成两份缓存和失效问题，因此两者职责必须分开。

### 为什么选择 TipTap？

普通 `textarea` 难以支持结构化段落、ParagraphKey、选区引用、查找替换和后续扩展。TipTap 提供 ProseMirror 文档模型，能对长章节进行结构化编辑。代价是包体较大，所以编辑器独立懒加载，并用 100,000 字符测试与性能预算约束。

### 为什么生产前端通过 Nginx 代理 `/api`？

浏览器始终访问同源地址，避免 CORS、Cookie/Authorization 差异和多环境硬编码。Nginx 的 `BACKEND_UPSTREAM` 指向后端宿主映射；前端代码只请求 `/api`。

### 为什么 SSE 使用流式 fetch，而不是原生 EventSource？

原生 EventSource 不能设置 `Authorization` Header，而当前认证是内存 Bearer JWT。把 Token 放进 URL 会泄露到历史、日志和代理。流式 `fetch` 可以安全发送 Header，同时实现事件 ID 去重、重连和取消。

### 为什么主题切换时取消语义颜色过渡？

文字、背景和边框分别过渡时，中间帧可能形成低对比度组合，axe 会正确捕获这种瞬时 WCAG 失败。现在主题语义颜色作为一组即时切换，只保留位移和阴影等不影响可读性的动画。

## 四、后端与数据问题

### 为什么使用 JPA，同时仍然写 SQL 迁移？

JPA 简化聚合持久化和乐观锁；Flyway SQL 明确控制表、约束、索引和 pgvector。Hibernate 使用 `ddl-auto=validate`，只验证实体与数据库一致，不擅自修改生产结构。

### 为什么同时使用乐观锁、唯一约束和悲观锁？

它们解决不同问题：

- 普通资源编辑使用 `version/expectedVersion` 乐观锁，冲突返回 409。
- 业务唯一性由数据库唯一约束兜底，例如章节号和幂等键。
- 审批提交是高风险临界区，用悲观锁锁住 WorkflowRun，防止两个审批同时提交。

### 为什么向量放在 PostgreSQL，而不是独立向量数据库？

当前规模下，项目所有权、可见性、关键词和向量结果需要一起过滤。pgvector 让这些条件在同一数据库完成，部署和一致性更简单。当前使用精确余弦距离；数据规模显著增长后，应先基准测试 HNSW/IVFFlat，再评估独立向量服务。

### 为什么用户角色通过 Flyway V15 增加？

角色是持久业务字段，不能只在代码里写死账号名。V15 为 `app_user` 增加受约束的 `USER/ADMIN` 字段；认证响应返回角色，JWT 把角色映射为 `ROLE_USER/ROLE_ADMIN`。公开注册仍默认 `USER`，避免任意注册成为管理员。

当前只完成角色契约和权限基础设施，还没有管理后台或管理员专属接口。

## 五、Skill 熔炉技术问题

### 为什么使用 28 套显式模板，而不是让模型临时猜？

素材性质与目标 Skill 类型是两个独立维度。成品正文用于“基础契约”和用于“审稿检查”的学习目标完全不同。7 × 4 的显式矩阵可测试、可审阅、可稳定复现，避免模型每次生成不同的表单建议。

### 为什么模板只在两个选项都选中后填充？

单独知道素材标签或 Skill 类型都不足以确定任务目标。提前填充会制造错误暗示，也可能覆盖用户正在输入的内容。

### 为什么用户修改后切换模板不能自动覆盖？

推荐内容只是起点，不是权威答案。前端分别追踪学习重点和素材说明是否被修改；切换条件时只更新未修改字段，并给出“保留当前内容/使用新模板”的明确选择。

### 为什么原文存储和导出契约分离？

熔炼需要原文证据才能审阅，但导出 Skill 不应携带受版权保护或私有素材。数据库保存私有来源、段落和哈希；契约只包含被接受的抽象规则、证据引用和结构化上下文，ZIP 不包含原始 TXT 或粘贴文本。

### 为什么 TXT 有 10 MiB 单文件限制？

它在可导入长稿和内存/请求风险之间折中。系统还限制最多 20 个文件、合计 20 MiB，并限制解析编码，避免一次请求消耗过多内存或以错误编码生成不可追溯文本。

## 六、实际遇到的问题与解决方案

| 问题 | 根因 | 解决方案 | 如何避免复发 |
| --- | --- | --- | --- |
| Docker 无法绑定 9090 | Windows/Hyper-V 保留了 9063—9162 端口段 | 本地 Prometheus 改为 19090，Grafana 改为 13080 | 在 `.env` 配置宿主端口；启动脚本读取并显示真实值 |
| 后端默认 8080 不适合当前机器 | 本地端口环境与默认配置不同 | 当前工作区使用 18080，容器内仍保持 8080 | 区分容器端口和宿主端口，不改正式 API 路径 |
| 单独重建前端后登录不跳转 | Compose 回落到默认 `BACKEND_UPSTREAM=:8080` | 通过根启动脚本注入实际后端 18080 | 完整环境优先使用 `Start-StoryWeaver.ps1` |
| Compose 报 orphan container | 历史服务名变更留下容器 | 核对容器后按需使用 `--remove-orphans` | 删除前确认目标，避免误删数据卷 |
| 深色主题 axe 对比度失败 | 主题切换中间帧混合了新旧颜色 | 语义前景/背景/边框即时切换 | 可访问性测试覆盖浅色、深色和切换过程 |
| 跳过导航焦点偶发失败 | 焦点时序与页面路由切换竞争 | 保持可聚焦主区域并做串行键盘回归 | 真实浏览器测试，不只检查 DOM 属性 |
| Node/pnpm engine 不匹配 | 系统 pnpm 11 或 Node 22 与项目锁定版本不符 | 使用 Node 24 + Corepack pnpm 10.30 | 保留 `engines`、`packageManager` 和 engine-strict |
| Windows Java 格式检查失败 | 手工补丁产生不同换行/格式 | 运行仓库 Spotless 格式器后 `verify` | Java 变更交付前执行 `mvnw spotless:apply` |
| Java 23 测试出现 Mockito 动态 Agent 警告 | 当前 Mockito inline mock maker 会在运行时自附加 Byte Buddy Agent | 目前不影响 Java 21 目标构建和测试结果；升级 JDK/Mockito 前按官方建议显式配置测试 Agent | CI 固定 Temurin 21，并把该警告作为后续依赖升级检查项 |
| 旧账号无法直接删除 | 多张表通过外键引用用户 | 先备份，再删除项目聚合让 CASCADE 清理，最后删除用户 | 先查询 FK delete rule，在事务内执行 |
| “青铜城”只存在于测试页面 | Playwright fixture 会拦截 API，不是真实数据库 | 通过正式 API 创建项目、正典资产和世界书条目 | 明确区分 Demo fixture 与正式数据 |
| 动态模板可能覆盖手写内容 | watch 直接赋值没有区分推荐和用户输入 | 使用字段级 customized 状态与恢复按钮 | 为切换条件和“不覆盖”写单元测试 |
| TXT 中文解码不稳定 | BOM、UTF-8 和 GB18030 来源混杂 | 显式探测允许编码，失败即阻止熔炼 | 不使用平台默认编码悄悄继续 |

## 七、为什么没有选择其他方案

### 为什么不是 React？

React 同样可行，但当前团队和既有代码已经围绕 Vue Composition API、Vue Query 与 Element Plus 建立完整测试和组件体系。迁移不会带来与成本相称的业务收益。

### 为什么不是 Node.js 后端？

Node.js 可以提供 API，但当前系统高度依赖事务、JPA 乐观锁、Spring Security、Micrometer、Spring AI 与 Java Validator。重写会扩大风险，没有解决当前瓶颈。

### 为什么不是 WebSocket？

当前实时需求主要是服务器向客户端推送工作流进度，SSE 足够简单并支持 HTTP 基础设施。只有出现高频双向协作编辑或客户端实时指令通道时，才需要 WebSocket。

### 为什么不是 Kubernetes？

当前是单机开发/演示环境。Kubernetes 会增加镜像仓库、Ingress、Secret、存储、探针和集群运维成本。生产多实例、弹性和故障隔离成为明确需求后再引入。

### 为什么没有 OpenAPI 自动生成？

当前后端尚未提供受版本控制的 OpenAPI 文件，前端只能依据实际 DTO 维护类型。这是已知缺口。后续应由后端生成并纳入 CI，再逐步替换手工类型，而不是由前端猜测 schema。

## 八、排障顺序

遇到页面不可用时，按以下顺序检查：

1. `docker compose ps` 是否显示前后端、数据库和 Redis 健康。
2. 前端 `/healthz` 和后端 `/actuator/health/readiness` 是否为 HTTP 200。
3. 前端容器的 `BACKEND_UPSTREAM` 是否指向实际后端宿主端口。
4. 浏览器 Network 是否收到标准 Problem Details；401、409 和 500 需要分别处理。
5. Flyway 是否成功到最新版本，Hibernate 是否完成实体校验。
6. 工作流问题同时检查持久化状态、SSE event ID 和后端日志。
7. 模型问题检查 API Key、模型健康、预算和 Usage，而不是先修改业务数据。
8. 数据删除或迁移前先备份并验证目标 ID、外键和事务范围。

## 九、何时应该重新评估技术选型

出现以下信号时应重新评估，而不是因为流行趋势更换技术：

- 单体无法满足独立扩缩容或团队发布节奏，且模块边界已经稳定。
- pgvector 精确检索在真实数据规模下超过延迟预算。
- SSE 无法满足明确的双向实时协作需求。
- HS256 单体 JWT 无法满足多服务、外部身份提供商或强吊销需求。
- Compose 无法满足生产高可用、滚动部署、Secret 与持久卷治理。
- 手工 TypeScript DTO 已频繁产生契约漂移，OpenAPI 自动生成收益明确。

技术选型的目标不是“使用最多技术”，而是在当前业务规模下以最少不可控复杂度保证数据正确、流程可追溯和后续可演进。
